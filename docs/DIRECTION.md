# Direction — 판단과 결정 기록

[PLAN.md](PLAN.md)(원본 기획안)를 검토하고 내린 결정입니다. **둘이 충돌하면 이 문서가 우선합니다.**
PLAN.md는 원칙과 장기 설계의 참고서로 두고, 지금 만드는 범위는 [PROTOTYPE_SPEC.md](PROTOTYPE_SPEC.md)가 정합니다.

결정마다 번호를 붙입니다. 뒤집을 때는 지우지 말고 상태를 `폐기`로 바꾸고 이유를 적습니다.

## 요약

PLAN.md는 **무엇을 하지 않을지**는 잘 정했지만, **처음에 무엇을 할지**는 덜 정했습니다.
분량 대부분이 MVP 이후의 인프라에 쓰였고, 프로젝트의 성패가 걸린 두 가지 —
**기억에 남는 행성 외형**과 **도착 카메라** — 는 원칙만 있고 방법이 없습니다.
그래서 Prototype의 무게중심을 인프라에서 이 두 가지로 옮깁니다.

## 결정

### D1. username 진입과 개인 별자리를 추가한다 — `채택`
**PLAN.md의 공백.** 핵심 장면은 "나의 작은 세계"(단수)인데, 개발자는 repo가 여러 개이고 그 repo들은 주제에 따라 은하 곳곳에 흩어집니다. 사람들은 `owner/repo`보다 username을 먼저 입력합니다 (Git City의 진입도 username입니다).

- 입력창은 `username`과 `owner/repo`를 모두 받는다.
- `username`이면 그 사람의 행성들을 선으로 이은 **개인 별자리**를 먼저 보여주고, 그중 하나를 골라 항해한다.
- 개인 별자리는 PLAN.md F장의 "겹쳐지는 관계로서의 Constellation" 정의를 그대로 따른다. 새 계층을 만들지 않는다.
- fork는 개인 별자리에서 기본 제외한다 (지저분해지고, 대부분 "내가 만든 것"이 아니다).
- 공유 문구는 순위가 아니라 분포다: "내 별자리는 web·graphics·CLI 세 지역에 걸쳐 있다."

### D2. 착륙은 Prototype에서 뺀다 — `채택`
PLAN.md는 "착륙 개발이 프로젝트를 삼킴"을 위험으로 꼽아 놓고 Prototype 범위에 착륙을 넣었습니다. 서로 모순입니다.

- Prototype이 검증할 두 가지(자기 행성으로 알아보는가 / 안내 없이 다음 세계를 고르는가)는 **궤도에서 이웃 방향의 하늘을 보여주는 것만으로** 테스트할 수 있다.
- 착륙은 이 두 가지를 통과한 뒤 별도 실험으로 넣는다.
- 다만 지형 함수는 처음부터 "나중에 표면에서도 같은 값을 내는" 형태로 짠다 (PLAN.md N-2: orbit과 surface는 같은 지형 함수).

### D3. 행성 정체성은 "큰 실루엣 하나"로 만든다 — `채택`
PLAN.md는 "seed 기반의 기억할 만한 지형"을 여러 번 요구하지만 방법이 없습니다. 이 프로젝트의 성패가 여기에 걸려 있습니다. 절차적 생성에서 흔한 함정이 **"만 개의 오트밀 그릇"**(수학적으로는 전부 다르지만 사람 눈엔 같아 보임)입니다.

- 사람이 기억하는 것은 노이즈 디테일이 아니라 **큰 실루엣 하나**다.
- 손으로 디자인한 **랜드마크 원형 8–12개**를 만든다 (거대 분지, 고리 협곡, 첨탑, 쪼개진 반구, 계단식 고원, 적도 띠 …).
- seed는 원형 하나와 방향·비율·위치를 고른다. 노이즈는 그 위의 질감이다.
- 언어 구성 → 재질 무늬, 활동 → 그 위의 빛 레이어. 활동이 지형을 바꾸지 않는다.
- 검증 방법: **오트밀 테스트** (PROTOTYPE_SPEC E2).

### D4. Prototype은 npm 생태계 하나로 제한하고, 관계 해석은 기존 데이터를 쓴다 — `채택`
PLAN.md가 "가장 어려운 부분"으로 꼽은 `package → repo` 매핑은 이미 풀어 둔 곳이 있습니다.

- 주 소스: **ecosyste.ms** packages API — npm 패키지 정보와 GitHub repo 정보(GitHub repo ID 포함)를 함께 준다. 데이터 라이선스 **CC BY-SA 4.0** (출처 표시 필요, 파생 데이터도 같은 라이선스). 익명 시간당 5,000회.
- dependency 목록: **deps.dev** requirements API — 최신 버전의 `dependencies`, `peerDependencies`. (처음엔 npm registry를 썼지만 동시 요청 16개에 429와 `retry-after: 409`를 받았다. ecosyste.ms의 버전 API는 peer를 주지 않는다.)
- GitHub 토큰 없이 시작한다. GitHub REST(비인증, 시간당 60회)는 테스트 참가자 repo 몇 개에만 쓴다.
- 생태계를 하나로 묶으면 화면의 모든 항로가 실제로 확인 가능한 연결이 된다 (K8).

### D5. Prototype 기술 범위를 대폭 줄인다 — `채택`
PLAN.md N장은 방향은 맞지만 지금 읽으면 인프라부터 짓고 싶어집니다. MVP에 들어갈 때 다시 펴 보는 참고서로 둡니다.

| PLAN.md 항목 | Prototype에서 |
|---|---|
| Leiden community detection, 관계 가중치 0.35/0.25/… | 안 함. TF-IDF + UMAP 한 번 |
| sector 좌표, floating origin, local frame 분리 | 안 함. 반경 1000 단위 좌표 하나 (float32로 충분) |
| tile, manifest, CDN | 안 함. JSON 파일 하나 (repo 3천–1만 개 ≈ 1–3 MB) |
| PostgreSQL, 큐, worker | 안 함. 파이썬 스크립트 + 로컬 캐시 |
| lazy ingestion | 안 함. 테스트 참가자 repo는 include 목록으로 미리 넣는다 |
| Next.js | **Vite + React + R3F**. URL·공유 메타데이터가 필요해지는 MVP에서 Next.js 검토 |
| 좌표 장부 | **함**. 작지만 핵심 원칙(K5)이라 처음부터 `ledger.json`으로 둔다 |

### D6. 좌표 장부는 Prototype부터 둔다 — `채택`
- `repo ID → sector + pos + placement version`을 `data/ledger.json`에 기록하고 버전 관리에 포함한다.
- 파이프라인을 다시 돌려도 장부에 있는 행성은 움직이지 않는다. 새 repo만 기존 이웃의 가중 중심 근처 빈자리에 놓는다 (PLAN.md E-6의 축소판).
- 설명·topics·dependency가 거의 없는 repo는 **관계 미확정 지역**(은하 바깥 고리)에 둔다.

### D7. 데이터 소스와 출처를 화면에 밝힌다 — `채택`
- 정보 패널에 관측 repo 수, 데이터 출처(ecosyste.ms, deps.dev, GitHub), 관측 시점을 표시한다.
- "GitHub 전체"를 암시하지 않는다. Prototype은 "npm 생태계의 표본 N개"라고 말한다.

### D8. 은하 모양은 데이터가 만든다 — `D14로 수정` (PLAN.md E-3 재확인)
- 나선팔을 장식으로 강제하지 않는다. UMAP 결과를 두께 있는 원반으로 눕히기만 한다.
- 결과가 밋밋하면 표본 구성이나 특징 가중치를 바꾸지, 좌표에 모양을 덧씌우지 않는다.

### D9. 관계는 "항로 전파"로 좌표에 넣는다 — `채택` (E1)
PLAN.md E-1의 신호별 가중치 합산(dependency 0.35, 의미 0.25 …) 대신, 설명·topics·dependency 토큰으로 특징 벡터를 만들고 **확인된 항로로 이어진 이웃의 평균을 섞는다** (α=0.5, 1회).
- 이유: React처럼 수백 개 repo가 딛고 선 행성이 자기 생태계 한가운데로 간다. 전체 이웃 일관성은 거의 잃지 않는다 (0.843 → 0.833).
- 근거: [experiments/E1-galaxy.md](experiments/E1-galaxy.md) §배치 1.

### D10. owner·조직은 배치 신호로 쓰지 않는다 — `D16으로 수정` (E1, PLAN.md E-1 수정)
PLAN.md는 조직을 "약한 보조 신호"로 두었다. 실제로 약하게(0.15) 넣었더니, 설명이 짧은 개인 repo들은 주제와 상관없이 한곳에 뭉쳤다 (이웃의 98%가 자기 repo).
- 같은 사람·조직의 행성은 **개인 별자리 선**으로 잇는다 (D1). 가까이 놓지 않는다.
- 근거: [experiments/E1-galaxy.md](experiments/E1-galaxy.md) §배치 2.

### D11. 도착 구도는 랜드마크가 정한다 — `채택` (E1, D13에서 보완)
도착할 때 랜드마크가 화면 중심에서 좌상단(빛 쪽)으로 26° 비켜난 자리에 온다. 은하 중심이 행성 뒤에 오는 구도보다 우선한다.
- 이유: 랜드마크가 반대편에 있으면 "만 개의 오트밀 그릇" 중 하나로 보인다 (E1 갤러리).
- PLAN.md G의 "33–41초: 독특한 지형이 반대편에서 나타남"과는 반대다. 정체성을 먼저 보여주고, 돌려 보면 실루엣으로 다시 보인다.

### D12. 은하 → 지역 → 행성계 → 행성의 계층을 보이게 한다 — `계층은 유지, 행성계의 뜻은 D16으로 바뀜` (E1b, 사용자 피드백)
PLAN.md F는 System을 필수 계층에서 뺐다. 실제로 보니 계층이 없으면 멀리서는 이어진 덩어리, 가까이서는 흩어진 점이었다.
- **지역**: 관계망의 큰 생태계. 지역 사이에 빈 공간을 둔다.
- **행성계**: 지역 안에서 더 가깝게 묶이는 4–36개. 중심별 둘레의 궤도에 놓고, 공통 주제에 가까울수록 안쪽 궤도.
- **중심별은 repo가 아니다.** 구성원이 공유하는 주제의 집계 표현이다. "repository 하나 = planet 하나"(PLAN.md F)는 그대로.
- 별자리(개인 별자리 포함)는 여전히 계층이 아니라 겹쳐지는 관계 표현이다.
- 행성계 소속과 궤도는 장부에 기록한다. 이름은 매번 지금 구성원으로 다시 짓는다 (재분류는 이름에만 반영, PLAN.md E-7).
- 새 repo는 가장 비슷한 행성계의 바깥 궤도로 들어간다. 근거: [experiments/E1b-structure.md](experiments/E1b-structure.md).

### D13. 행성은 자기 별의 빛을 받는다 — `채택` (E1b)
행성계가 생기면 빛은 별에서 와야 한다. 카메라에 붙은 조명은 별이 보이는 순간 어긋난다.
- 지형(정체성)은 그대로 두고 행성의 **방향만** 정한다: 도착 카메라에서 별빛이 좌상단에서 비껴 들어오고, 랜드마크가 그 빛 쪽 26°에 오도록.
- 관계 미확정 행성(행성계 없음)은 카메라 기준 주광을 쓴다.

### D14. 지역을 나선팔 위에 놓는다 — `폐기` (E1c에서 채택 → 사용자가 D17을 택함)
D8은 "나선팔을 장식으로 강제하지 않는다"였다. 실제로 보니 모양이 없는 은하는 은하로 보이지 않았다.
- 모양을 **장식으로 덧씌우지 않고, 지역의 자리로 만든다**: 핵은 모두가 딛고 선 기반 지역, 팔은 기반에서 응용으로, 같은 팔에는 서로 많이 이어진 지역.
- 중심에서 바깥으로 가는 방향이 "기반 → 응용"이라는 의미를 가진다.
- 이웃 일관성은 거의 그대로 (0.712 → 0.705). 근거: [experiments/E1c-spiral.md](experiments/E1c-spiral.md).

### D15. 원경은 은하 사진의 문법으로, 근경은 광물 천체도로 — `채택` (E1c, 사용자 피드백, PLAN.md K 수정)
PLAN.md K는 "NASA 사진처럼 보이는 우주"를 피하라고 했다. 사용자는 실제 은하 사진의 "보는 맛"을 원했다.
- **멀리서**: 나선팔의 별빛·성운·먼지띠, 빛나는 핵, 배경 별과 먼 은하. 모두 **연출 층**이고 선택할 수 없으며 repo 수로 세지 않는다 (K7). 정보 패널에 밝힌다.
- **가까이서**: 행성·명판·궤도는 그대로 광물 천체도 (무광 표면, 가는 선, 작은 활자).
- 연출은 데이터가 정한 나선을 따른다. 데이터가 없는 곳에 팔을 그리지 않는다. (D17 이후: 나선 대신 행성계·지역이 있는 자리를 따른다)

### D16. 행성계 = 계정 — `채택` (사용자 결정, D10·D12 수정)
Git City의 "사람 = 건물"처럼, **계정 하나가 행성계 하나**다.
- **별 = 계정** (repo가 아니다). **행성 = 그 계정의 공개 repo** (fork 제외, 계정당 최근 push 순 100개까지 — 넘으면 "일부만 관측"이라고 밝힌다).
- **궤도 = 만든 순서** (궤도 하나에 행성 하나 — D19). 첫 repo가 별에 가장 가깝다. 행성계가 그 사람의 시간 기록이 되고, 새 repo는 자연스럽게 바깥 궤도로 들어간다 (장부 원칙과 맞는다).
- D10(owner를 배치 신호로 쓰지 않음)을 뒤집는 게 아니다: 그때 문제는 "가까우면 관련 있다"가 거짓이 되는 것이었다. 지금은 "같은 별을 도는 이유 = 같은 사람이 만들어서"가 화면에 드러난다. 주제 관계는 항로와 지역이 맡는다.
- 주제로 묶던 행성계(D12, E1b)는 없어진다. 계층(은하 → 지역 → 행성계 → 행성)은 그대로.
- 개인 별자리 선(D1)은 행성계로 대신한다.

### D17. 은하와 모양은 데이터가 정한다 (B) — `채택` (사용자 결정, D14 폐기)
사용자: "repo를 아무 기준으로 채워 넣는 건 별로. 데이터가 만든 모양으로."
- **은하 = 비슷한 일을 하는 계정들의 큰 무리** (계정 관계망의 Leiden, 낮은 해상도). **지역** = 은하 안의 더 작은 무리.
- 생태계·언어로 은하를 나누지 않는다. 나누면 한 사람의 repo가 여러 은하로 흩어져 "계정 = 행성계 하나"가 깨진다. 언어는 은하의 **이름**(두드러진 언어·주제)과 행성의 재질로 드러난다.
- 계정의 자리는 계정 벡터(그 계정 repo들의 평균)의 UMAP이 정한다. 나선팔은 강제하지 않는다. 은하마다 자기 주축으로 조금 납작하게 눕히는 것(원반)만 한다.
- 여러 분야에 걸친 계정은 은하 사이 경계에 설 수 있다. 그것도 정직한 모습이다.
- 원경 연출(D15)은 나선이 아니라 **행성계·지역이 실제로 있는 자리**를 따라 빛난다. 은하마다 빛깔이 다르다.

### D18. 검색한 계정을 그때 들인다 (Git City 방식) — `채택` (사용자 결정)
GitHub 전체(공개 repo 수억 개)를 미리 넣을 수 없다. 대신:
- 표본 계정으로 우주를 먼저 만들고, **모르는 username을 검색하면 서버가 GitHub에서 가져와** 고정 모델(어휘·IDF·SVD)로 계정 벡터를 만들고, 가장 비슷한 계정들의 은하·지역 근처 빈자리에 행성계를 놓는다. 그 뒤로는 모두에게 보인다.
- 기존 행성계는 하나도 움직이지 않는다. 한 번 들어온 계정은 장부(`data/universe.db`)에 남는다.
- 새 계정의 repo가 이미 있는 행성에 의존하면 그 자리에서 항로가 생긴다 (패키지 → deps.dev → 기존 행성).
- 들이는 동안에도 우주를 둘러볼 수 있다 (PLAN.md G "API를 기다리는 시간을 끝없는 warp로 숨기지 않는다").
- GitHub 비인증은 시간당 60회(계정 30개). `GITHUB_TOKEN`을 주면 5,000회. 한도를 넘기면 ecosyste.ms로 대신 가져온다.

### D19. 궤도 하나에 행성 하나 — `채택` (사용자 결정)
사용자: "태양계면 궤도 하나에는 행성 하나만 있어야 하지?" 배치 v4는 궤도 하나에 행성 5–25개를 나란히 놓았다.
- k번째로 만든 repo가 k번째 궤도를 혼자 돈다. 궤도 반지름 = 6 + 2k (행성 지름 1.2–1.8보다 넓다). 새 repo는 바깥에 궤도 하나를 더한다.
- 궤도 위 각도는 계정과 궤도 번호로 정하고, 바로 안쪽 두 궤도의 행성과 4 이내로 붙지 않게 한다.
- 행성계가 커져서(repo 100개면 반지름 약 200, 전에는 36) 은하·우주도 약 3.9배 커졌다. 화면의 거리 기준은 은하 반지름에 맞춰 함께 늘어난다 (`World.scale`).
- 궤도가 7만 개라 선으로 그리지 않고 행성계마다 사각형 하나에 셰이더로 그린다. 화면에서 궤도가 촘촘하면 선을 옅게 한다.
- 보고 있는 행성계의 행성은 자리는 그대로 두고 점의 최소 크기·밝기만 올린다 (궤도가 많으면 행성이 몇 px밖에 안 된다).

## 사소한 정정

- **"repo ID는 JS 정밀도 때문에 문자열로"**(PLAN.md N-2) — GitHub repo ID는 현재 10억대(예: 2026년 9월 생성 repo가 1,378,288,761)라 `2^53`(약 9×10^15)과 거리가 멉니다. 문자열로 두는 건 괜찮지만(다른 호스트·미래 대비), 이유가 정밀도는 아닙니다.
- **관계 가중치**(PLAN.md E-1) — 신호 종류가 적은 Prototype에서는 의미가 없습니다. 신호가 3개 이상 들어오는 V1에서 다시 봅니다.
- **fork의 source_name** — ecosyste.ms 데이터에서 `fork: false`인데 `source_name`이 채워진 경우가 있습니다 (예: chalk/supports-color). fork 계보는 `fork: true`일 때만 믿습니다.

## 열린 질문

- 여러 분야에 걸친 계정: 행성계는 한 은하에만 설 수 있다. 은하 이름에 언어가 들어가 생태계처럼 보이는 것("TypeScript · mcp"인데 TypeScript는 36%)과, 다른 은하 쪽 성격의 행성을 어떻게 드러낼지.
- 테스트 참가자 5명을 어디서 구할지 (0–10 star repo 소유자 최소 3명).
- 사운드를 Prototype에 넣을지. 기본은 무음으로 완결, 여유가 있으면 도착 화음 하나.
- 데이터 라이선스(CC BY-SA)가 향후 상용화 계획과 맞는지. 맞지 않으면 MVP 전에 GitHub API 직접 수집으로 바꾼다.
